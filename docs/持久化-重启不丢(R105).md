# 持久化：为什么现在就必须做，以及怎么做的（R105）

## 0. 起因
爷爷问：「为什么要等上线才换成 Redis/SQLite？」

**我上一轮说错了。**「等上生产再换」是错的判断 —— 因为**部署即重启**这件事现在每次都在发生，
所以内存态丢失不是"未来的风险"，而是**当前正在发生的缺陷**。

## 1. 为什么现在就必须做

| 理由 | 证据 |
|---|---|
| **每次部署都硬重启 mailfarm** | `services.json` 里 mailfarm `restartOnDeploy=true`；实测部署后 `/healthz` 的 `uptime_s` 只有 **103.7 秒** |
| 重启 = 正在等的验证码凭空消失 | `store=memory` 时 `boxes`/`messages` 全在内存，进程一没就归零 |
| 注册流程正好卡在"等码"那一步 | `pool-supply` 的 `mail-wait` 最长等 90 秒；这期间重启 → 注册必失败 |
| 崩溃不设防 | 机房/进程任何异常退出都直接丢光 |

## 2. 为什么没用 SQLite（实测结论，不是偷懒）

- 本机 Node **v24.21.0**：`require(String.fromCharCode(110,111,100,101,58,115,113,108,105,116,101))` **可用**（`DatabaseSync, StatementSync, constants, backup`）。
- 服务器 Node **v22.23.3**：不加开关 **报错**，必须 `--experimental-sqlite` 才能用。
- 而我们的启动器 `deploy/run-service.ps1` 是：`$argList = @($script) + $scriptArgs` —— **node 的启动参数只能写在脚本前面**，
  现有机制加不上去（写后面会被当成脚本参数）。`NODE_OPTIONS` 也不收 `--experimental-*` 这类开关。
- **所以选了「零依赖 JSONL 追加日志 + 快照压缩」**：同样达成"重启不丢"，且不需要任何启动参数、不引入依赖。
- 想上真 SQLite 的路只有一条：**把 mailfarm 的服务换成 node-v24.21.0 + `NODE_SKIP_PLATFORM_CHECK=1`**（已实测 node24 在该服务器可跑）。
  爷爷点头我就换，切换只动 `services.json` 一行 + store 实现。

## 3. 实现（`scripts/mailfarm-server.js`）

新增环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `MF_STORE` | `memory` | `memory` / `file` |
| `MF_STATE_DIR` | `state` | 相对仓库上一级；服务器上显式设为 `C:\yunshudu\state\mailfarm`（**在 app 之外，robocopy /MIR 不会碰**） |
| `MF_STATE_FILE` | 空 | 直接指定 jsonl 路径（留空则取 `<dir>/mailfarm.jsonl`） |
| `MF_SNAPSHOT_EVERY` | 500 | 攒够多少行追加日志就做一次快照压缩 |

事件格式（每行一条 JSON）：
```
{"t":"box","a":"hlxxxx@ytu.baby","d":"ytu.baby","c":1760000000000,"e":1760003600000}
{"t":"msg","a":"hlxxxx@ytu.baby","m":{"ts":1760000012,"sender":"...","subject":"...","codes":["483920"],...}}
```
- **写**：`acquire` 建箱、`deliver` 收信 → `appendFileSync` 追加一行（追加写，最坏情况只丢最后一条）。
- **读**：启动时 `initStore()` 重放整个文件，跳过已过期箱体，重建 `boxes`。
- **压**：行数 ≥ `MF_SNAPSHOT_EVERY` → 用当前内存态重写文件（`写 .tmp` → `rename` 原子替换）。
- `/healthz` 与 `/v1/stats` 增加 `store`（`memory`/`file`）与 `state_path` / `persist_loaded`。

## 4. 自测（新增 `scripts/mailfarm-persist-selftest.js`）

**PASS=13 FAIL=0**，关键那几条：
```
PASS  healthz.store = file
PASS  重启前取码 = 909090
PASS  状态文件已写入(>=2 行)
-- 杀掉进程(SIGKILL)后重启 --
PASS  *** 重启后取码仍是 909090(持久化生效) ***
PASS  重启后 messages 仍有该封
PASS  触发 compact 后取码仍正常
PASS  compact 后文件首行是快照(box)
```
（`SIGKILL` = 模拟崩溃，连清理都来不及 —— 这都活下来了，说明不是"优雅退出才保存"的假持久化。）

## 5. 与上游的差距

上游 `45.207.214.211:8099` / `45.207.214.98:8099` 的 `/healthz` 都还写着 **`"store":"memory"`** ——
也就是说 **上游自己也没做持久化**，我们这一步是**反超**。

## 6. 还没做（可继续）

- 真 SQLite（要先把服务切到 node 24）。
- Redis（多实例共享；上游按域分节点就是绕开这个问题）。
- 消息级 TTL 清理（现在只有箱级 TTL + 每箱条数上限）。
