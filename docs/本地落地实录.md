## B. 故障排查全过程（401 → 200 的最后一公里）

### B-1 现象

`test-call.js 8` 全量 401：

```
call#1..8  HTTP 401  {"code":"","message":"Invalid token (request id: 2026...d9d6...)"}
```

### B-2 定位

令牌确实存在且有效（SQLite 读回）：

```
#1  user=1  local-test-token  status=1  quota=5000000
    sk-OY6xM6Br1G0MmZSmxtKulGhhNnUgOmafZpq8Zd0TBaJFYfRF
```

而 `runtime\test-token.txt` 里躺着的是：

```
sk-OY6x**********YfRF
```

**根因**：`setup-channels.js` 用 `GET /api/token/` 的返回值拼 key（`'sk-' + t2.key`），
但 **new-api 的令牌列表接口只返回脱敏 key**，于是把脱敏串当成了真实 key 写进文件。

### B-3 修复

改从 SQLite `tokens` 表读真明文，覆写 `runtime\test-token.txt`（len=51）。
修复后调用立刻通过鉴权，进入下一层报错：

```
HTTP 400  Model MiniMax-H3 price not configured ...
code: model_price_error
```

### B-4 二次修复

新增 `scripts\set-pricing.js`，`PUT /api/option/` 写入：

| option | 值 |
|---|---|
| `ModelPrice` | `{"MiniMax-H3":0.047945205479,"MiniMax-M3":0.047945205479, ...原值保留}` |
| `ModelRatio` | `{"MiniMax-H3":1,"MiniMax-M3":1, ...}` |
| `CompletionRatio` | `{"MiniMax-H3":1,"MiniMax-M3":1, ...}` |

价格与 `45.207.214.163:3000` 实测的 `model_price=0.047945205479` **一致**。
三个 PUT 均返回 `{"success":true}`。

## C. 多渠道池实测（20 次压测）

### C-1 客户端视角

| call | HTTP | 说明 |
|---|---|---|
| 1–3 | 401 | 打到 **B 组**（9922 永远欠费）→ 402 被映射成 401 |
| 4 | 200 | A 组 **sk-a1**（1/2） |
| 5 | 200 | A 组 **sk-a2**（1/2） —— 轮询换号 |
| 6 | 200 | A 组 **sk-a1**（2/2） |
| 7 | 401 | 随机命中 B 组 |
| 8 | 200 | A 组 **sk-a2**（2/2）—— 至此 2 把 key 全部耗尽 |
| 9–20 | 401 | A 组内部只剩"超额"key，B 组恒欠费，池子见底 |

### C-2 上游视角（mock 逐请求日志）

```
[mock][B] key=sk-b1  used=0/0  POST /v1/chat/completions -> 402 insufficient balance
[mock][A] key=sk-a1  used=1/2  POST /v1/chat/completions -> 200 (MiniMax-H3)
[mock][A] key=sk-a2  used=1/2  POST /v1/chat/completions -> 200 (MiniMax-H3)
[mock][A] key=sk-a1  used=2/2  POST /v1/chat/completions -> 200 (MiniMax-H3)
[mock][A] key=sk-a2  used=2/2  POST /v1/chat/completions -> 200 (MiniMax-H3)
[mock][A] key=sk-a1  used=2/2  POST /v1/chat/completions -> 402 insufficient balance
[mock][A] key=sk-a2  used=2/2  POST /v1/chat/completions -> 402 insufficient balance
```

**成功的调用数 = 池容量（2 key × 2 格 = 4）**，一格不多、一格不少。
"算力池"的黑箱到此完全打开。

### C-3 渠道内部状态（`GET /api/channel/?p=0`）

```

    status_code_mapping = {"402":"401"}
    channel_info = {"is_multi_key":true,"multi_key_size":2,"multi_key_status_list":null,
                    "multi_key_polling_index":1,"multi_key_mode":"polling"}

```

`multi_key_polling_index` 随请求递增 → 轮询调度被直接观测到。

## D. 机制小结（可直接照抄到自己的站）

```
渠道.key        = "sk-a1\nsk-a2\nsk-a3"      # 换行分隔 => 一个渠道 = 一个号池
mode            = multi_to_single            # 建渠道必填，否则池子不生效
multi_key_mode  = polling | random           # 轮询 or 随机取号
auto_ban        = 1                          # 失效 key 自动摘除
status_code_mapping = {"402":"401"}          # ★灵魂：额度耗尽当成"这把 key 挂了"
```

一句话：**402 映射成 401 ⇒ 单 key 熔断 ⇒ 轮询换号 ⇒ 池子续上就继续跑。**
不映射 402 的话会触发渠道级故障，整池一起挂。
