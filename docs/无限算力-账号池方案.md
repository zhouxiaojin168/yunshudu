# 无限算力 · 账号池方案（复刻 + 落地）

> 这份文档回答三件事：① 那两个站（`45.207.214.163:3000`、`xuetianai.com`）的「算力」到底哪来的；
> ② 我们怎么用同一套手法把「算力」做成接近无限；③ 每条代码在哪、怎么改、怎么验。

---

## 0. 先把「无限算力」说准（不吹）

市面上所谓「无限算力」，没有任何一家是真无限的。它一定是下面这个恒等式的工程化：

```
池子可用算力 = Σ(每个上游账号的余额)  -  在飞预占
每天新增     =  账号数 × 每账号每日签到额度  +  手工/批量补号
```

所以「无限」= **补给速度 ≥ 消耗速度** 的持续补充机制。要成立必须同时具备四件事：

| # | 机制 | 我们落在哪 |
|---|---|---|
| 1 | **账号池**：N 个上游账号汇成一个池，客户只买 credit | `scripts/h3-platform-pool.js` |
| 2 | **换号重试**：单号余额耗尽(402) 自动换下一个，客户无感 | 同上 `runPoolTask()` |
| 3 | **签到补分**：定时把每个号的每日免费额度拿满 | 同上 `checkinTick()` |
| 4 | **持续补号**：健康号数低于阈值就自动补进新号 | `scripts/pool-supply.js` |

> 边界（必须写清楚）：**本方案不含「绕过上游风控批量自动注册」的逻辑**。
> 注册被抽象成一份可配置的工作流（`config/pool-register.json`），验证码走接码平台，
> 上游一旦收紧签到/注册，池子就会掉——这是所有这类站的共同命门，不是我们的实现缺陷。

## 1. 两个站的手法拆解

### 1.1 `http://45.207.214.163:3000/`（样本站，现已下线）

形态：**服务端账号池（平台池）**。当时能看到的证据链：

- 客户侧只出现一种商品：**credit（算力）**，没有模型价格表、没有渠道分组；
- 出片接口是一站式的（提交任务 → 拿 `task_id` → 轮询结果），客户拿不到上游账号；
- 上游错误原样冒出来过：`402 plan balance has run out`（余额不足）、`429 + Retry-After`（限流）、
  `400 could not be read or decoded ... call upload_temp_url`（沙箱读不了公网 URL）
  —— 这几条只可能来自「服务端拿着账号去调上游」这一种架构。

结论：**账号是站方的资产，客户买的是额度**。这类站要扩容，就是不断往池子里加号 + 每天签到。

### 1.2 `https://xuetianai.com/`（雪天，在线）

形态：**New API（或同源分支）**。判定依据是它 `/api/pricing` 回来的字段结构：
`model_ratio` / `model_price` / `*_groups` / `quota_type` —— 这套命名是 New API 家族的方言，不是 OpenAI 原生结构。

它的「算力」其实来自**渠道池**：

```
客户 Key -> New API 选渠道(按模型/分组/权重/优先级) -> 渠道里的上游 Key -> 上游
```

- 同一个模型可以挂**多条渠道**，每条渠道带 `weight`（权重）+ `priority`（优先级）；
- `group`（分组）+ `model_ratio` 决定「按什么价卖给客户」；
- 因此它的「算力」= **上游 Key 的数量 × 每条 Key 的余额**；Key 越多、权重轮询越平均，越像「无限」。

### 1.3 两者区别（一句话）

| | 45.207.214.163:3000 | xuetianai.com |
|---|---|---|
| 池子在哪 | **服务端**（账号池，客户碰不到） | **网关侧**（渠道池，Key 级轮询） |
| 卖什么 | credit（按条/按秒折算） | 按 token / 按次（模型价格表） |
| 扩容动作 | 往池子加账号 | 往渠道加 Key |
| 泄露风险 | 低（账号不出站） | 中（渠道 Key 泄露 = 上游被白嫖） |
| 适配成本 | 高（要按上游接口写适配） | 低（New API 控制台点几下） |

**我们两层都做**：`h3-platform-pool` 复刻第一种（服务端账号池），`new-api` 的「渠道 + 权重 + 默认渠道」复刻第二种。

## 2. 我们的实现：三层

```
  客户 ──► New API(3000) ──► 平台池(9940) ──► 上游(wallet/checkin/task)
          渠道池/权重/计费      账号池/预占/换号      真上游 或 沙箱(9941)
                                    ▲
                                    │ 补号 + 签到
                               pool-supply(9950)
```

| 层 | 文件 | 端口 | 职责 |
|---|---|---|---|
| 网关 | new-api（外部二进制） | 3000 | 卖价、分组、渠道权重、给客户发 Key |
| 账号池 | `scripts/h3-platform-pool.js` | 9940 | 账号资源、最肥优先、预占+实扣、402 换号、签到 |
| 补给 | `scripts/pool-supply.js` | 9950 | 保号（低于阈值补号）、定时签到、管理面 |
| 适配 | `config/pool-adapter.json` | — | 上游只有 3 个接口，换上游只改这个 JSON |
| 沙箱 | `scripts/mock-official.js` | 9941 | 演练用上游，用来证明整条链真的通 |

### 2.1 账号池的账本（SQLite）

`accounts` 表就是「池子」本体，关键列：

| 列 | 含义 |
|---|---|
| `token` | 上游账号 token（UNIQUE，是账号唯一身份） |
| `credits` | 本地记账余额（成功后被上游真实余额覆盖） |
| `held` | **在飞预占** = 未结算任务占用的额度 |
| `cap` | 单号封顶，防止单号被撸爆 |
| `healthy` / `fail_reason` | 健康位 + 死因（`ACCOUNT_EXPIRED` / `PROBE_AUTH_FAILED` / `CHECKIN_AUTH_FAILED`） |
| `cooldown_until` | 429 退避截止时间 |
| `checkin_count` / `success_count` | 签到次数 / 成功出片数（可观测） |

调度核心（`pickAccount` + `hold`/`release`）：

- **最肥优先**：按 `credits - held` 倒序取，避免小号被反复打；
- **预占**：提交前 `held += cost × 2`，成功后按上游真实 delta 结算，失败必 `release`；
- **402 换号**：余额耗尽 → 同步真实余额 → 换下一个号，最多 3 个；
- **401/403 判死**、**429 退避**，都不会污染客户请求（客户侧永远看不到换号）。

### 2.2 「无限」的补给站（pool-supply）

守护循环每 60s 跑一轮：

1. `GET /pool/stats` 数健康号；
2. 健康号 < `SUPP_POOL_MIN`（默认 5）→ 补号，最多补到 `SUPP_POOL_MAX`（默认 200）；
3. 每 10 轮调一次 `POST /pool/checkin` 把全池当日免费额度领满；
4. 状态写 `state/pool-supply.json` + `logs/pool-supply.log`。

**三个补号源**（按顺序尝试）：

| 源 | 输入 | 适用 |
|---|---|---|
| ① 农场文件 | `state/farm-accounts.jsonl`，每行 `{"label":..,"token":..}` | **能立刻跑通**：自己养/买好的号直接倒进来 |
| ② 注册工作流 | `config/pool-register.json`：`http` / `sleep` / `sms-get` / `sms-wait` / `emit` 五种步骤 | 有可用注册接口时全自动补号 |
| ③ 接码平台 | `SUPP_SMS_GET`（取号）/ `SUPP_SMS_POLL`（查码）/ `SUPP_SMS_KEY` | 注册要手机验证码时配合 ② |

> 农场文件里 **不写 `credits`** 最省事：入库时池子会主动 `wallet` 探一次真实余额；探到 401/403 直接判死，
> 不会让池子「虚胖」（一堆 0 余额的号假装健康）。

## 3. 上游适配器：换上游不动代码

池子只认 3 个接口，全写在 `config/pool-adapter.json`：

```json
{
  "name": "mock-official",
  "base": "http://127.0.0.1:9941",
  "auth": { "type": "body", "field": "token" },
  "endpoints": {
    "wallet":  { "method": "POST", "path": "/official/v2/wallet",  "map": { "credits": "balance" } },
    "checkin": { "method": "POST", "path": "/official/v2/checkin", "map": { "credits_before": "before", "credits_after": "after", "delta": "delta" } },
    "task":    { "method": "POST", "path": "/official/v2/task",    "map": { "task_id": "task_id", "result_url": "video_url", "wallet_before": "wallet.before", "wallet_after": "wallet.after", "delta": "wallet.delta" } }
  }
}
```

- `auth.type` 支持 `body` / `bearer` / `header`（上游把 token 放哪儿就写哪儿）；
- `map` 是 **JSON 路径映射**（支持 `a.b.c`），把上游字段翻译成池子的统一字段；
- `base` 可被环境变量 `H3P_UPSTREAM` 覆盖（优先级：环境变量 > JSON > 内置默认）。

**接真上游只要三步**：改 `base` → 改 3 个 path → 改 `map`。代码一行不用动。

## 4. 部署形态（服务器 114.66.16.225）

| 服务 | 端口 | 计划任务 | 说明 |
|---|---|---|---|
| new-api | 3000 | `yunshudu-new-api` | 网关/卖价/发 Key |
| h3-platform-pool | 9940 | `yunshudu-h3pool` | 账号池引擎 |
| pool-supply | 9950 | `yunshudu-pool-supply` | 补号 + 签到守护 |
| h3-mock-official | 9941 | `yunshudu-h3-mock` | **沙箱上游**，接真上游后停掉 |
| edge-proxy / cloudflared / tunnel-watch / portal | 80+8080 / — / — / 8899 | 各自任务 | R70 已上线 |

约定：

- 运行态一律放 **`C:\yunshudu\data` / `C:\yunshudu\state` / `C:\yunshudu\logs`**；部署用 `robocopy /MIR`，
  现已显式 `/XD` 排除 `state`、`data`、`logs`、`runtime\data`、`secrets.txt`，**部署不会删账号池数据**；
- 管理密钥（`H3P_ADMIN_KEY`）只写在服务器 `C:\yunshudu\secrets.txt`，由 `run-service.ps1` 的 `envFrom` 注入，**不入库**；
- 池子只监听 `127.0.0.1`，公网进不来；对外只通过 new-api 渠道暴露。

## 5. 管理接口速查

账号池 `9940`（要带 `x-admin-key`）：

| 方法 路径 | 作用 |
|---|---|
| `GET /healthz` | 存活 + 在飞数 |
| `GET /pool/stats` | 全池账号 + 审计（换号/签到/结算） |
| `POST /pool/accounts` | 加一个号（省略 `credits` 会自动探余额） |
| `POST /pool/accounts/bulk` | **批量加号** `{"accounts":[{label,token,credits?}]}`，返回 `imported/skipped/probed` |
| `POST /pool/checkin` | 立刻全池签到 |
| `POST /pool/keys` | 发一个池子侧 Key（`unlimited` 可无限） |
| `POST /pool/reset` | 清空池子（**会连带清 Key**，慎用） |
| `GET /v1/public/stats` | 免 Key 展示池子规模（给客户看的门面） |

补给站 `9950`：

| 方法 路径 | 作用 |
|---|---|
| `GET /supply/healthz` | 存活 |
| `GET /supply/stats` | 供给侧状态 + 池子健康度 |
| `POST /supply/guard` | 立刻跑一轮补号（`{"force":true}` 强制补） |
| `POST /supply/checkin` | 转发全池签到 |
| `POST /supply/import` | 批量导入账号 |
| `POST /supply/register` | 跑 N 次注册工作流（`{"n":2}`） |

## 7. 上线到真上游的清单

1. 拿到上游账号（自己养/买）→ 写进 `C:\yunshudu\data\farm-accounts.jsonl`（每行 `{"label":..,"token":..}`）；
2. 改 `config/pool-adapter.json` 的 `base` + 3 个 `path` + `map`（或在 `services.json` 里改 `H3P_UPSTREAM`）；
3. 在服务器 `secrets.txt` 里设一个强 `H3P_ADMIN_KEY`（别用默认值）；
4. 重启 `h3-platform-pool` / `pool-supply` 两个任务；
5. 在 new-api 里加一条渠道指向 `http://127.0.0.1:9940`（模型名对上池子的 `SPECS`），设好 `weight`；
6. 沙箱上游（`h3-mock-official`）确认不再需要后停掉。

## 8. 诚实的成本与风险

| 项 | 现实 |
|---|---|
| 账号来源 | 农场号要自己养/买；自动注册要过验证码 + 设备指纹 + 风控，成功率和成本都不确定 |
| 接码平台 | 要付费 key，本方案只对接，不内置任何绕过 |
| 签到额度 | 是否「每天发一次」完全取决于上游实现——**这是方案成立与否的关键前提，必须先实测** |
| 上游条款 | 多账号聚合、批量注册通常违反上游服务条款，被风控扫到会连带封号 |
| 「无限」 | 是「补给 ≥ 消耗」，不是数学意义上的无限 |

> 一句话：**这套代码把「账号池 + 换号 + 签到 + 补号」四件事做成了可运维的工程件；
> 池子能多大，取决于你能拿到多少合法可用的上游账号。**
